# Рабочее соглашение: Muse как worker над SlavikAI

Статус: согласовано владельцем 2026-11-16; уточнено по замечаниям к roadmap. Применять вместе с ROADMAP.md и STATE.md после их принятия.

## 1. Источник правды — файлы в репозитории

- Роадмап и очередь задач живут в репо: `ROADMAP.md` + `STATE.md`. Это канон.
- Почему файлы, а не чат: чат сжимается, контекст одной сессии конечен; огромный роадмап в чате съедает рабочую память. Файлы переживают сессии, их видят все участники (владелец, техдиректор, программный директор, Codex, Muse), они версионируются в git.
- Владелец может диктовать роадмап в чат — Muse сама переносит его в файл. Каноническая копия — только файл в репо.

## 2. Нарезка: роадмап → эпики → тикеты

- Один тикет = одна задача = одна ветка = один PR.
- Размер тикета: работа на один заход — прочитать код, изменить, прогнать `make check`, починить, доложить. Больше — резать.
- Каждый тикет самодостаточен: не зависит от памяти о прошлых тикетах, ссылается на файлы и роадмап.
- В каждом тикете обязательно:
  - **ЧТО** — простыми словами, что должно получиться;
  - **ЗАЧЕМ** — какая польза пользователю;
  - **КРИТЕРИЙ ГОТОВНОСТИ** — как проверить, что настоящее (негативные тесты, новые входы, проверка postcondition);
  - **РАЗРЕШЕНИЯ** — что можно удалять/менять, что нельзя. Ответ на «удаляем или оборачиваем?» — без него работа не начинается.
- Порядок: сначала то, что разблокирует остальное — единый контракт исполнения, затем persistent browser. Параллельных тикетов не начинать.

- Второе дерево — linked `git worktree` того же репозитория, не отдельная копия и не backup. Третье дерево запрещено без нового решения владельца.
- Строго один тикет = одна ветка от актуального `origin/main` = один PR, без параллельных тикетов. Служебная `muse/slavikai-rebuild` — не PR-ветка. Тикетные ветки пока не удалять.
- Исправления PR по review производятся в той же рабочей ветке тикета (или отдельной correction branch, когда это оговорено и не нарушает очередь), с новым CI/review.
- Подробная процедура и защита двух worktree: [dev_workflow.md](docs/workflow/dev_workflow.md).

## 4. Цикл работы

1. Muse берёт следующий тикет из очереди.
2. Реализует **только во втором worktree Muse** на отдельной PR-ветке, прогоняет `make check`.
3. Пушит в GitHub, дожидается ревью Codex в GitHub и зелёного CI.
4. Если независимое ревью Codex текущего HEAD чистое, CI зелёный, `make git-check` прошёл и блокеров нет, Muse **вручную** обновляет `origin/main` fast-forward push текущей PR-ветки **из своего worktree**, проверяет точный SHA и статус `merged` на GitHub, затем обновляет служебную ветку. Это делегированное владельцем действие; исходное дерево владельца не трогать. Если GitHub branch protection не разрешает такой push — STOP и вопрос владельцу, без обхода. **GitHub auto-merge и merge queue не включать**. Делегирование ограничено roadmap-PR Muse.
5. При блокерах — чинит, что может; если finding требует решения владельца — спрашивает владельца.
6. Чекпоинт после каждого тикета/PR: доклад — что сделано, что дальше.

## 5. Решения: кто что решает

- Мелкие инженерные решения внутри тикета — Muse (она лучше знает, как кодить). Владельца не дёргать.
- Развилки «так или иначе» (реальные альтернативы реализации, даже если оба варианта технически допустимы) — **обязательно с владельцем до реализации**. Muse предоставляет варианты, trade-offs, рекомендацию и влияние на следующие тикеты; не выбирает сама архитектурную ветку. Мелкие внутренние решения внутри уже утверждённого способа реализации остаются за Muse.
- Подтверждения: Muse присылает вопрос в чат на телефон владельца, когда нужно — необратимое действие, sudo (точную команду называет заранее), finding, требующий решения владельца. Владелец на связи и подтверждает. Merge после чистого ревью подтверждения не требует — он входит в цикл.
- Задачи Muse даёт только владелец через роадмап. Никто другой (включая техдиректора) задачи напрямую не даёт.
- PR ревьюит Codex в GitHub (независимый ревьюер). Muse себя сама не ревьюит.

## 6. Что нужно от владельца

- Роадмап (приоритеты, порядок).
- ПК включён и в сети (Tailscale), пока идёт работа.

## 7. Честные ограничения

- Токены — не проблема. Проблема — контекст одной сессии: длинная работа живёт только в файлах (роадмап, тикеты, `STATE.md`).
- Muse не видит экран владельца и не кликает в GUI; в аккаунты владельца не логинится.
- Если ПК спит/выключен или хост ребутнулся — работа останавливается, фоновые процессы умирают; состояние должно быть в файлах.

## 8. Архитектурные решения (зафиксировано 2026-11-16)

- **Local bridge** — для SlavikAI на ПК владельца: демон на хосте с ограниченным API по Unix socket или localhost HTTP, как Desktop Commander. SSH — только если агент и ПК — разные машины.
- **Браузер** — свой, отдельный, с persistent профилем (Browser Session Resource), не основной Chrome владельца. Логин вручную один раз, дальше агент работает в авторизованной сессии.

## 10. Готовность roadmap и качество тикетов

- Полный инвентарь текущего плана: **62 последовательно исполняемых тикета**; это план, а не 62 уже утверждённых реализации.
- Эпики E00–E03 (31 тикет) описаны для исполнения, но каждый начинается с повторной проверки актуального кода и соблюдения owner gates.
- Эпики E04–E08 (31 тикет) — **предварительный backlog**. Их описания нельзя считать готовыми к реализации без полного уточнения каждого тикета до начала соответствующего эпика.
- Перед открытием очередного эпика Muse обязана детализировать его тикеты по шаблону: ЧТО, ЗАЧЕМ, verified touchpoints/unknown, зависимости, scope, delete-vs-wrap, шаги, positive/negative/E2E acceptance, postconditions, разрешения и запреты, evidence, test/review/CI gates. Развилки в проектировании — сначала владельцу.
- Следующий тикет не начинается до merge предыдущего. Если предстоящий эпик не детализирован и не согласован, в `STATE.md` ставится `BLOCKED: ROADMAP_REFINEMENT`.
