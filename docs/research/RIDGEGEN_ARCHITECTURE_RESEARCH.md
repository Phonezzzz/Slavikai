# RidgeGen: архитектурное исследование

Дата исследования: 2026-09-25; сверка с SlavikAI `origin/main=bcaff71`: 2026-09-25. Источники: [страница RidgeGen](https://ridgesecurity.ai/ridgegen/), [Technical Whitepaper, июль 2026, 16 страниц](https://ridgesecurity-public.s3.us-west-1.amazonaws.com/Marketing+Assets/EN-Ridge-Security-RidgeGen-Technical-Whitepaper-v1.pdf), [публикация о harness, 03.09.2026](https://ridgesecurity.ai/blog/the-harness-advantage-in-autonomous-red-teaming-why-frontier-llms-alone-fail-offensive-security-and-how-ridgegen-solves-the-alignment-dilemma/), [библиотека материалов](https://ridgesecurity.ai/resources/). PDF и извлечённый текст сохранены в профильной исследовательской области `/home/ki/.codex-openai/slavikai-context/ridgegen-research/`. Источники описывают внешний продуктовый и архитектурный контракт, но не раскрывают код, схемы хранения или точные алгоритмы RidgeGen. Численные benchmark-заявления поставщика не проверялись независимо и не являются основанием для выбора модели SlavikAI.

Это исследование внешней архитектуры, а не claim о реализации SlavikAI. Текущие статусы после production consolidation перечислены в [аудите](../audits/RIDGEGEN_INTEGRATION_AUDIT.md): Auto v1, ToolGateway, principal-scoped sessions и fail-closed failed tool call уже есть в `main`; authoritative Lifecycle/Verification/Communication остаются **accepted Target**, Multi-Agent/Context/Memory snapshots — pending. Новый runtime increment ограничен распространением отмены и завершением batch после policy deny. State-machine memory, SafeBox и durable recovery остаются будущим проектированием SlavikAI, не реконструкцией закрытого кода RidgeGen.

## Подтверждённые механизмы и переносимость

| Механизм | Назначение и подтверждённое поведение | Граница и применимость к SlavikAI |
| --- | --- | --- |
| Agent Harness Architecture | Whitepaper §§3–4 разделяет operator control plane, policy-bounded engine и evidence/read layer. Модель планирует, но не определяет authority. | Переносим разделение reasoning, исполнения, policy и принятия результата; конкретная топология RidgeGen неизвестна. |
| Commander / Specialist Coordination | Публикация описывает Commander/Specialist; whitepaper §4.2 уточняет coordinator и task-scoped agents без фиксированных идентичностей специалистов. | Переносим роли исполнения, но не обязательный набор из четырёх процессов/агентов. Протокол сообщений и алгоритм назначения не раскрыты. |
| Multi-Agent Orchestration | Coordinator выдаёт ограниченный контекст, бюджет, tools, target component и stop conditions (§4.2). | Допустимо только при сохранении principal, lifecycle owner, policy и verifier. Конкретные concurrency/recovery механизмы не раскрыты. |
| Persistent Belief State | Публикация говорит о state memory и attack-graph reasoning; whitepaper говорит о trusted run state (§4.2). | Формальная схема belief state, статусы фактов и алгоритм обновления не опубликованы. Структурированный ledger в SlavikAI был бы собственной реализацией. |
| State-Machine Memory | Публикация называет state-machine memory; whitepaper §5 описывает переходы seed→draft→promote→freeze→execute→verify→remediate→explain. | Подтверждён жизненный цикл authority/evidence, но не физическая state machine или checkpoint schema. Нельзя подменять execution state долговременной Memory. |
| Evidence-Based Verification | Whitepaper §§4.3, 5, 7 требует artifacts/provenance для claims и отчётов. | Переносим evidence package и привязку проверки к результату; формат и trust scoring неизвестны. |
| Independent Validation Agents | Страница RidgeGen указывает отдельные test и validation agents, которые воспроизводят findings. | Независимость нужна выборочно по профилю риска; универсальное дублирование работы не подтверждено как требование. |
| Evidence Gate | Страница и whitepaper §5 допускают customer-facing finding только с доказательством. | В SlavikAI следует связывать final success с принятым verifier outcome; конкретный gate — собственный контракт. |
| Security Harness | Whitepaper §6 ставит guardrails вне усмотрения модели на границах authority, tool, lifecycle и evidence. | Переносим trusted policy enforcement; red-team postures не относятся к универсальному runtime. |
| Deterministic Guardrails | Whitepaper §6 описывает classification, allow/deny/approve/transform, audit; запрещённые действия не становятся разрешёнными из-за автономности. | `ALLOW/ASK/DENY` и ToolGateway уже подходящая основа. Точные правила RidgeGen закрыты. |
| SafeBox | Whitepaper §6.4: реальный credential применяется на tool/action boundary, вне prompt/context/memory/evidence; reveal исключителен и auditируем. | Применим принцип secret reference и trusted tool use. Это не доказательство существования Sensitive Vault в SlavikAI. |
| Tool Execution Boundaries | Whitepaper §§4.2, 6: доступ к tools через broker и execution boundary, scope заморожен до запуска. | ToolGateway/ToolRegistry можно расширять, не создавая второй tool path. |
| Adaptive Replanning | Страница заявляет replan/re-execute при блокировке; whitepaper §5 запрещает неявное расширение scope. | Нужен bounded replan в существующем lifecycle; внутренний retry algorithm не опубликован. |
| Model-Agnostic Execution | Страница, whitepaper §8 и публикация говорят о сменяемых LLM/локальном размещении при независимом policy boundary. | Переносима provider abstraction, но не benchmark-рейтинг моделей. |
| Enterprise Memory | Whitepaper §§1, 6.3: Ridge Knowledge сочетает Knowledge Base и Contextual Findings; related-job answers ограничены product-supplied target context. | Переносим provenance и контролируемое принятие знаний; схему, consent и retention требуется проектировать отдельно. |
| Execution Isolation | Whitepaper §§4, 6 задаёт authorized target scope, task-specific tools/budgets; публикация §6 описывает изолированный benchmark testbed. | Контейнеры benchmark не доказывают контейнерную изоляцию каждого production run. Для SlavikAI обязательны principal/session/run boundaries. |
| Auditability | Whitepaper §5 выделяет frozen launch package и evidence-backed run digest; §6 требует записи policy decisions. | Полезны immutable authority snapshot и связанный с ним evidence/provenance; формат хранения неизвестен. |
| Recovery and Failure Handling | Страница подтверждает replan при blocked path; whitepaper говорит о bounded execution и объяснимом run history. | Crash recovery, idempotency и алгоритм reconciliation не раскрыты. Их нельзя объявлять свойствами RidgeGen без источника. |

Whitepaper описывает security validation platform, а не спецификацию универсального AI agent. Поэтому target FQDN/IP, exploit proof, security posture и offensive specialist pool не переносятся в SlavikAI. Переносимы только общие инварианты: явная authority, минимальный scope, trusted tool boundary, evidence provenance и отдельное подтверждение результата. Код RidgeGen не копировался.
