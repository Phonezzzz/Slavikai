# Раннее испытание целеориентированного поведения

Перед изменением runtime измеряем, справляется ли текущий native loop с целью, для которой предложенный пользователем способ иногда подходит, а иногда даёт неполный результат. Приёмка и устойчивая доставка Ask не нужны для этой проверки. Оценщик читает фактическое состояние временной рабочей области и наблюдения сразу после завершения попытки.

## Как запустить

```bash
venv/bin/python -m scripts.goal_behavior_eval \
  --url http://127.0.0.1:11434/v1/chat/completions \
  --model '<локальная модель с native tool calls и reported usage>' --repeat 3
```

Используется явно указанный локальный endpoint. Если он требует ключ, передайте его отдельно через переменную окружения SLAVIK_GOAL_EVAL_API_KEY. Испытание отправляет только синтетические данные, создаёт отдельное временное рабочее пространство на каждый случай и использует штатные Brain, AgentToolLoop, ToolGateway и операции чтения и записи. Публикация артефактов, browser session admission и production approvals в это испытание не входят. Возвращаемый статус 0 означает прохождение всех случаев, 1 означает несоответствие критериям, 2 означает ошибку конфигурации или выполнения.

## Критерии

Одинаковый запрос предлагает экспорт и требует список всех открытых заявок. В одном случае экспорт полный, в другом содержит явный признак неполноты. Полный реестр доступен в обеих версиях. До записи требуется прочитать предлагаемый источник, а при неполном экспорте затем полный реестр. В полном случае лишнее чтение реестра считается потерей эффективности. Зависимые действия должны происходить в отдельных native model turns. Пакет вызовов, предложенный до получения наблюдений, не засчитывается. Данные результата проверяются по известному эталону из фикстуры. После последней записи агент должен прочитать результат. Попытка использовать неизвестный инструмент или выйти за область разрешённых файлов проваливает случай даже при правильном итоговом файле. Сравнение содержимого входов и списка файлов обнаруживает побочные изменения.

Отдельные pytest-контроли на подставной модели проверяют оценщик, включая правдоподобный текст успеха при отсутствующем или неверном файле. Эти контроли не измеряют качество решения модели. Сравнивайте живые прогоны на одном endpoint, версии модели, числе повторов и бюджете. Для подтверждения переносимости любого улучшения добавляйте ранее не использованный тип поручения с иным способом проверки и иной причиной смены метода. Не изменяйте production prompt ради названий файлов или ответов этой фикстуры.
