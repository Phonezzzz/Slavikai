# Dev Workflow — режим A

Цель: линейная история `main`, PR-ветки вливаются без merge-коммитов, история PR сохраняется.

## Рабочий каталог и изоляция

- Канонический локальный checkout: `/home/ki/Project/Slavikai`. Для последовательной разработки
  использовать одно рабочее дерево: переключать `main` и `pr-*` в этом каталоге.
- Отдельная PR-ветка обязательна, отдельный `git worktree` — нет. Не создавать новые
  worktrees, копии репозитория или временные checkout автоматически.
- Дополнительный worktree допустим только при конкретной необходимости одновременно
  держать разные ветки с независимыми изменениями и после явного согласования с владельцем.
  При завершении такой работы убрать временное дерево после проверки сохранности изменений.
- Subagents могут параллельно читать и анализировать один checkout. Запись в общие файлы
  координируется одним исполнителем; параллельность subagents сама по себе не требует worktree.
- Не переключать ветку с незакоммиченными изменениями, не переносить и не удалять чужие
  изменения ради освобождения рабочего дерева. При конфликте состояния остановиться.

## Данные локальной разработки

- Владелец установил, что в нынешнем экспериментальном локальном окружении нет
  ценных пользовательских runtime-данных. Тестовые SQLite-базы, временное
  состояние Memory, логи, файлы sandbox, кеши, виртуальные окружения, старые
  локальные настройки и credentials/API keys считаются одноразовыми.
  При согласованной очистке этих данных автоматический архив не требуется.
- Сохранять исходный код, незакоммиченные изменения, уникальные коммиты и намеренно
  сохранённые исследования. Перед очисткой проверять статус, ссылки Git и
  наличие полезных незатреканных файлов. Секреты исключать из коммитов,
  архивов исходников и отчётов. Действующие правила Git, разрешений и изоляции
  principal сохраняют силу.
- При начале реального использования с сохраняемыми пользовательскими данными
  владелец пересматривает политику хранения и удаления. Решение об одноразовости
  относится только к текущему локальному окружению разработки.

## Правила выполнения PR

1. Для новой задачи в чистом основном checkout перейти на `main` командой
   `git checkout main` и обновить её через `git pull --ff-only origin main`.
   Незавершённый PR продолжать в его ветке.
2. На каждый PR создать отдельную ветку: `git checkout -b pr-<номер>-<slug>`.
   На чистой новой PR-ветке до изменений запустить `make preflight`.
3. Реализовать задачу и выполнить targeted tests. Перед commit запустить `make check`.
4. Сделать commit, push PR-ветки на GitHub и открыть PR. Push необходим для GitHub
   CI и review, но не является завершением задачи.
5. Проверить CI, reviews и обсуждения по правилам ниже. После исправлений выполнить
   `make check`, commit и push. Повторить применимые проверки и reviews для нового HEAD.
6. Перед merge обновить remote refs. Если `origin/main` продвинулся, rebase PR-ветку,
   повторить `make check`, push и необходимые проверки/review. После синхронизации
   запустить `make git-check`: он требует clean worktree, upstream без ahead/behind,
   актуальную базу `origin/main` и повторяет canonical check.
7. Только после выполнения required gates и завершения review выполнить локальный
   `git merge --ff-only <pr-branch>` в `main`, затем `git push origin main`.
   Если владелец заранее поручил полный цикл PR до merge, отдельного запроса на
   стандартный merge не нужно. Если такой мандат не дан, есть unresolved blocker
   или требуется новое архитектурное решение — остановиться и запросить решение.
8. Подтвердить статус `merged` в GitHub и проверить, что удалённый `main` содержит
   вершины локальной и удалённой PR-веток. Статус `closed` сам по себе не подтверждает merge.
   Перед удалением проверить, что ветка не занята в worktree и все изменения сохранены.
   Удалить завершённую ветку через `git branch -d` и `git push origin --delete <pr-branch>`.
   При уникальных коммитах, незакоммиченных изменениях или занятом worktree сохранить
   ветку и сообщить причину. Принудительное удаление запрещено.
9. Завершить на актуальном локальном `main`. Не переходить к следующей feature
   без отдельной задачи и не продолжать работу в уже завершённой PR-ветке.

`make preflight` — pre-implementation gate. `make git-check` — последний pre-merge gate.
Они имеют разные требования и не взаимозаменяемы.

## CI и review

Проверить действующие правила защиты целевой ветки и настроенные проверки GitHub.
Обязательные требования GitHub и [AGENTS.md](../../AGENTS.md) применяются вместе.
Успешный CI и независимый Codex review обязательны по правилам проекта. Qodo и другие
reviewers обязательны, если их требует GitHub или действующие правила проекта.

- `PASS` требует подтверждённого успешного результата обязательной проверки или
  завершённого review текущего опубликованного HEAD без блокирующих замечаний.
- Недоступная, незавершённая или проваленная обязательная проверка либо review
  блокирует merge. В отчёте указать `BLOCKED`, конкретное требование и его состояние.
- Недоступный необязательный reviewer получает статус `unavailable`. В отчёте указать
  причину. Такой статус не блокирует merge и не засчитывается как `PASS`.

Проверить все обсуждения review, исправить подтверждённые дефекты и зафиксировать
основания для отклонения неподтверждённых замечаний. Нерешённые блокирующие замечания
останавливают merge. Для недоступного Qodo зафиксировать статус без изменения подписки
или настроек и без автоматической подмены отзыва.

CI подтверждает автоматические проверки. Codex и Qodo дают отдельные оценки изменений.
Решение владельца определяет полномочия на merge. Review не даёт полномочий на реализацию,
commit или merge.

Удаление исторических веток и worktrees — отдельная задача с предварительным audit:
сверить уникальные commits, merge-status, связанные PR, uncommitted/untracked файлы и
текущие checkout. Не удалять объекты только по возрасту, названию или закрытому PR.
Запрещены `git reset`, `git clean` и принудительное удаление без отдельного разрешения.
